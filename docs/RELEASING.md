# Releasing HermesKey

## Release philosophy

HermesKey releases should feel deliberate:

- changelog updated
- docs updated
- CI green
- release artifact generated
- release notes written by a human, not just auto-generated

## Checklist

- [ ] update `VERSION`
- [ ] update `CHANGELOG.md` and write `docs/releases/v$VERSION.md` (published as the GitHub Release body; use absolute links)
- [ ] run `make check` and `make package`
- [ ] verify install docs still match reality
- [ ] test `bash scripts/bootstrap.sh --local` on a fresh KDE test install **and** an upgrade (confirm existing config is preserved, the Settings launcher is the sole visible menu entry, and pinned legacy shortcuts still work)
- [ ] confirm microphone dictation, Unicode insertion, Settings save/restart, and `hermeskey-doctor` on the test machine
- [ ] merge release-prep PR; on `main`, pull the merged commit and confirm `VERSION`, changelog date, and release notes before tagging
- [ ] tag/push the release from the verified `main` commit only (with approval)
- [ ] verify GitHub Actions published the `.tar.gz` archive and handwritten release body
- [ ] independently download the published asset, inspect its version/provenance, compute SHA-256 locally, and submit the version + digest to `trusted_release_digest()` in `scripts/bootstrap.sh` for a separate reviewed PR. Do **not** fetch the expected checksum from the same release API response or update it automatically in CI. The default installer intentionally **fails closed** between publication and that reviewed digest merge.
- [ ] verify a tampered copy aborts before `tar` or `install.sh`, and that the new pinned release installs on a KDE test system. Confirm the standard installer resolves the new release only *after* the digest PR merges. Document a reviewed immutable bootstrap commit for higher-assurance users; the raw-main entrypoint itself is mutable.

## Helper commands

Check the repo:

```bash
make check
```

Build the release tarball:

```bash
make package
```

Cut a release using the helper script:

```bash
./scripts/release.sh
```

## Notes

- `scripts/release.sh` **and `scripts/build-release.sh`** require a clean Git checkout. Commit and review release notes/version changes before building. The archive is made only from tracked files at `HEAD` (not generated bytecode, untracked local configs, test leftovers or files merely staged for commit); repeated builds of the same commit are byte-identical.
- The release workflow publishes a `.tar.gz` archive when a `v*` tag is pushed.
- Hand-written release notes live under `docs/releases/`.
